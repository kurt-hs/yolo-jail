# GitHub Copilot CLI native TLS under macOS keychain isolation

**Checked 2026-10-29:** Public source at pinned revisions, and the [maintainer's native Mac SecurityServer audit](https://github.com/mschulkind-oss/yolo-jail/blob/f2a317c4b4515cb160d47dfbd6ea14d9bea86314/docs/lab-reports/2026-10-29-mac-securityserver-audit.md) on yolo `d159a57f0` (report blob `2b308915f3bbfb60cd683c0560fd57b10fe42acb`). This research did not execute a Mac test or Copilot. The shipped `com.apple.SecurityServer` deny stays; no owner credential, real login item, or Copilot API request was tested.

## Answer and boundary

**No: native TLS does not inherently require password access.** `SecTrustCreateWithCertificates` + `SecTrustEvaluateWithError` evaluated a public certificate chain under the unchanged yolo deny and rejected a self-signed chain. URLSession also fetched public HTTPS under that deny; curl and Node worked via their own CA inputs. Those native Mac counterexamples are **not** a Copilot fix. The failing path is the particular legacy SecureTransport `SSLHandshake` API used by Rust `native-tls`: its peer-key/CDSA setup contacts `com.apple.SecurityServer` even though the application asks to verify the *server certificate*, not to fetch an owner password. Seatbelt permits or denies that service by name, not by the caller's certificate-only intent. Client certificate/mTLS and private-key authentication are different operations. There is still **no demonstrated fix for current Copilot CLI native HTTPS under yolo's same-UID, SecurityServer-denied profile**. There are, however, transferable paths worth testing rather than waiting passively for an upstream release: identify the failing client and its verifier; select a *supported* verifier that works with the existing trust source, or build a licensed client with a different TLS feature if the implementation permits it; validate both accepted peers and rejected peers in the actual profile. [Mise has one measured example](../design/macos-native-tls.md#measured-on-the-maintainers-mac-2026-10-23), not a Copilot fix. A separate-account design isolates the owner's keychain by UID but does not make same-UID service access safe. Do not treat an HTTPS proxy as a TLS relocation when the sandboxed client still opens a CONNECT tunnel and verifies the peer itself.

It does **not** run Copilot or Safehouse.

The [same report's synthetic item table](../lab-reports/2026-10-29-mac-securityserver-audit.md#2-disposable-keychain-measurements) shows a **real yolo self `bash` launch** and `p0` blocking every tested secret/attribute query, enumeration, add, delete, lock and unlock on an unlocked file-based disposable keychain whose *file was readable in the workspace*. `p2` admitted those operations for the `-T /usr/bin/security` no-prompt specimen. With a **second** disposable keychain outside all readable roots, path-based queries failed under `p0` **and** `p2`: the client still needed file access. Therefore the service deny is a load-bearing barrier for the readable, trusted specimen; file deny is an independent control for this file-based, path-bound API. Neither experiment queried real owner passwords. Search-list/default metadata snapshots were unchanged; both fixtures were deleted. These are not universal ACL/daemon results: no data-protection `secd` item, pathless session operation, restrictive ACL for the Copilot process, Safehouse effective profile or Copilot request was tested. In particular, **do not run** the report's proposed `security lock-keychain -a` test on the owner's login keychain; any pathless control must instead use a separate disposable UID whose *sole* default is a synthetic fixture, if such isolation can be prepared without touching owner state.

The [Copilot regression report #5085](https://github.com/github/copilot-cli/issues/5085), still **open with zero comments** at this check, reports that 1.0.92 works while 1.0.93–1.0.95-2 fail with `errSSLBadCert` under a one-service deny. The author's bundled-runtime inspection associates the failing native request with `native-tls`, and their separate rustls-platform-verifier client succeeded. These are *reported observations*, not independent reproduction or evidence that 1.0.105 works. Separate [#4364](https://github.com/github/copilot-cli/issues/4364) reports a rustls-platform-verifier private-CA/standards error on a macOS enterprise MCP registry in 1.0.78; that is a trust-policy problem, not evidence of the SecurityServer failure. [#5081](https://github.com/github/copilot-cli/issues/5081) reports a Windows proxy `UnknownIssuer` regression at 1.0.93 and a tested 1.0.94-3 success, not a Mac fix. Both remained open on 2026-10-29. The public [1.0.105 changelog](https://github.com/github/copilot-cli/blob/main/changelog.md) and npm `@github/copilot` latest metadata were checked 2026-10-29; the latter identifies 1.0.105. Neither a version number nor absence of a TLS entry proves the current packaged path. The [official CLI reference](https://docs.github.com/en/copilot/reference/cli-command-reference) and [network settings](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/network-settings), checked 2026-10-28, documented HTTP/2 negotiation (`COPILOT_ENABLE_HTTP2`), proxy routing and CA inputs, but **no TLS-backend selector in those pages**. That bounded documentation search cannot exclude undocumented or new runtime features. MCP `--transport` and editor-extension settings are not such selectors.

**Mach service lookup** means locating a named macOS service; it is not an item-level credential authorization. The measured `p2` secret read is limited to an unlocked file-based keychain with a no-prompt ACL trusting `/usr/bin/security`; it does not establish access to every owner item. Apple's [Security access-control APIs](https://developer.apple.com/documentation/security/access-control-lists) describe per-item controls. Conversely, a file-read deny is not a proof that a daemon cannot operate on an accessible item for the same UID. Neither blanket item access nor safety follows from `SecurityServer` lookup alone. In yolo's [self profile](../../internal/macosuser/seatbeltdeny.go#L913-L916) the explicit deny includes `com.apple.SecurityServer`, `com.apple.securityd.xpc` and `com.apple.secd`, while [trustd.agent is allowed](../../internal/macosuser/seatbeltdeny.go#L685); account mode has a distinct UID boundary. No option below authorizes weakening these denies.

## Safehouse's Copilot keychain envelope: two separate answers

**Does it expose real, unrelated keychain secrets directly to Copilot?** At the **policy** layer, yes, it exposes the *route*: the selected `copilot` process (and a subprocess it launches under the same outer sandbox) may access the host user's keychain directory read/write and look up SecurityServer, securityd.xpc, secd, authhost, security.agent and trustd. It does **not** confine those grants to a Copilot service/account or a disposable keychain. A same-UID caller could request an unrelated item through Security.framework; whether that request yields secret bytes, metadata, a user-presence prompt, or an item-ACL denial depends on that item and the live Mac. **No real unrelated credential was queried; there is no demonstrated exposure of every real password or a verified exfiltration vulnerability.** The [native synthetic matrix](../design/macos-native-tls.md#mac-side-follow-up--audit-the-securityserver-boundary) is the safe way to resolve the capability question for specified item classes and controls, *not* a license to probe the owner's keychain. Even a successful synthetic read establishes capability under those ACL conditions, not access to every existing item.

**Does it let Copilot store its own auth?** **Yes at the policy level**: keychain item add/update/read and writable `~/.copilot` are allowed subject to macOS authorization. More importantly, GitHub's [current command reference](https://docs.github.com/en/copilot/reference/cli-command-reference#copilot-login-options), checked 2026-10-29, says a completed `copilot login` stores the token in the **system credential store**, falling back to a **plain-text file under `~/.copilot/` or `COPILOT_HOME` if no credential store is found**. Its [configuration-directory reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference#directory-overview) calls `config.json` automatically managed state including authentication. These are vendor-documented intended behavior and location, **not** a measured successful login under Safehouse or a proven macOS keychain callsite. The Safehouse [historical 1.0.2 investigation](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/docs/docs/agent-investigations/copilot-cli.md#credential-storage) specifically calls this macOS Keychain but cannot prove the implementation of 1.0.105. Its [BYOK E2E](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/tests/e2e/copilot.bats#L8-L80) skips GitHub login and uses a fresh HOME plus an OpenAI key; it cannot establish auth storage. A fresh HOME alone neither changes the Security.framework search list nor process UID.

GitHub's [pinned public changelog](https://github.com/github/copilot-cli/blob/84ee80ea6490ce02d6000439356a609fcefbb9ae/changelog.md) says **Copilot's own inner shell sandbox** defaults macOS keychain access off since 1.0.72. The [current config reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference#configuration-file-settings) documents `sandbox.userPolicy.seatbelt.keychainAccess` as `false` by default for *sandboxed commands*, configurable in `settings.json` (its wording differs from the older changelog's `/sandbox` UI wording). Neither changes the outer CLI process's Safehouse grant; a policy-only probe launched as a Safehouse-wrapped command models the outer process and descendants **before any optional additional Copilot inner sandbox**, not actual shell-tool permission. No supported **CLI auth-storage-disable/backend-selector** was found in these two official reference pages; environment tokens and `COPILOT_HOME` alter auth source or config location, not prove keychain avoidance on an actual login. An auth-storage switch, even if one were later confirmed, would not change native TLS's SecurityServer dependency.

The grant is **intentional and disclosed as an optional integration**, but for `copilot` it is not an opt-in at invocation: [profile metadata](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/profiles/60-agents/copilot-cli.sb#L4-L7) requires `keychain.sb`; the [planner](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/bin/lib/policy/plan.sh#L379-L382) includes required optional modules. [The module](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/profiles/55-integrations-optional/keychain.sb#L7-L42) grants broad home-keychain files and named service lookups. [Base](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/profiles/00-base.sb#L36) is deny-default; [render ordering](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/docs/docs/policy-architecture.md) permits final-deny overlays, so *effective* generated policy including workdir, enables, appended profiles and terminal rules must be captured for each run. [Launch](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/bin/lib/runtime/launch.sh#L39-L48) invokes `sandbox-exec` around the wrapped program; [its docs](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/docs/docs/debugging.md) say children inherit the sandbox. Its own [keychain test](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/tests/policy/integrations/keychain.bats#L31-L50) checks `find-certificate -a` exit status, not a secret read. A [docker-integration test](https://github.com/eugene1g/agent-safehouse/blob/f1c6a6a355b1d82cc3f4b267c53f1f9ce456f9af/tests/policy/integrations/docker.bats#L123-L151) checks login-keychain discovery and file access on its own host; **do not repeat its real login/search-list queries** in this audit. This comparison establishes grant composition, not native item outcomes or a bypass of macOS item ACLs.

**What yolo can learn:** inspect the generated effective policy, not the word "optional"; distinguish direct DB reads from mediated item queries, process UID from `HOME`, and kernel sandbox from item-level access control. Use a representative *synthetic* permissive item to measure whether the granted route admits unrelated secrets, plus a restrictive item to prove ACLs still matter. Yolo's [self deny](../../internal/macosuser/seatbeltdeny.go#L913-L916) and [dedicated account](../design/macos-user-model.md#4-what-the-second-account-buys-and-what-it-costs) are materially different boundaries. A positive read matching Safehouse's documented grant is an intentional trade-off, not automatically a flaw; only verified behavior contradicting a claimed protection, an unintended implicit broad grant, or demonstrated ACL bypass warrants vulnerability triage. No publication/disclosure follows from this source review.

## Reusable paths, ordered by boundary preserved

1. **Identify and select a supported in-process verifier — best candidate, unproven for Copilot.** Tracing the *actual* native HTTP request (from public callsites/vendor evidence and a separately authorized Mac witness) should establish which requests use SecureTransport/CDSA versus rustls and whether a supported selector exists. A [rustls-platform-verifier](https://github.com/rustls/rustls-platform-verifier) path that reaches trustd without the legacy SecurityServer call is a hypothesis from #5085 plus the mise witness, not a Copilot option yet. For another native binary, inspect its TLS feature graph/build flags rather than assuming `SSL_CERT_FILE` steers SecureTransport. A licensed build from available source with an alternate feature is conditional on source/license and reproducible packaging; Safehouse's old report does **not** establish that current Copilot's implementation is available to rebuild. **Shortlist for controlled investigation, not adoption.**
2. **Dedicated guest UID — valid isolation alternative, not a same-UID TLS mechanism.** SandVault's model may allow its own keychain while denying the owner's by account permissions. Yolo already offers [account mode](../design/macos-user-model.md#4-what-the-second-account-buys-and-what-it-costs); this is not a proposal to replace its profile or change its credential bridges. Independently verify guest-only keychain access, trust roots and exact current client behavior before claiming compatibility. **Existing option; test hypothesis.**
3. **Relocate TLS behind a credential-free, constrained broker only if TLS really terminates there.** A narrowly scoped trusted process could make a validated public-HTTPS request and hand back non-secret data under an explicit authenticated protocol. It requires a new trust-boundary design, restrictions on destinations/operations, error propagation and verification of both peer identity and keychain negative controls. A conventional HTTP proxy's `CONNECT` merely relays bytes: the sandboxed client still performs TLS. Moving OAuth tokens, arbitrary HTTP requests or the full client across this boundary is not approved. **Defer architecture; no existing workaround demonstrated.**
4. **Version pin or vendor fix.** #5085's reported 1.0.92 behavior makes a pin a compatibility experiment, not a durable transferable strategy: age, security fixes, supported behavior and auth/API compatibility need separate review. The issue remains open; a later vendor change must be verified in the exact build. **Do not automatically downgrade or assume waiting is the only route.**

**Rejected as boundary-preserving fixes:** Safehouse's Copilot keychain profile, SandVault's service allowance transplanted into self mode, a file-only keychain deny with permitted same-UID security services, disabling certificate validation, disabling the sandbox, intercepting private securityd RPC or `DYLD` calls. [Claude Code issue #29533](https://github.com/anthropics/claude-code/issues/29533) reports a related Go sandbox TLS failure (`gh` fails where curl works), so the verifier audit is a *general* native-client method, not Copilot-specific. That issue is closed as duplicate; its comment suggesting `GODEBUG=x509usecgo=0` was challenged by a later commenter unable to find the setting or make it work. Do not copy that unverified flag: yolo's actual [Go bundle override](../../internal/macosuser/cagodebug.go) is version- and trust-source-specific.
