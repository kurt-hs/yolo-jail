# Release CI fixture diagnoses, 2026-10-20

A [lab report](README.md). These observations distinguish test-fixture failures from a confirmed launcher regression and an unresolved cleanup-harness observation. They do not claim a release outcome.

## Observed

- **Run 39359722948, attempt 1** failed `check-go` and `check-macos`. The Linux test overwrote a possibly read-only capture-store hard link; the Mac fixture used Bash syntax its runner rejected. See the [cached-good fixture](../../internal/cli/cachedgoodrecovery_test.go#L496-L520) and [floor-probe fixture](../../integration/macosuserfloor_test.go#L181-L193).
- **Run 39374929076, attempt 1**, failed a macOS bounded-existence-probe assertion because its fake could answer before the deadline, and a Linux readiness test's setup-inclusive stopwatch (264.7 ms against 180 ms) although its late refusal assertion passed. These were fixture defects, not evidence that production exceeded either deadline. See the [probe test](../../internal/cli/stopgone_test.go#L288-L314) and [readiness test](../../internal/cli/run/perjailstartupdeadline_test.go#L127-L157).
- **Run 39379025920, attempt 1, macOS job 118483596973**, failed only `TestAFailedBackgroundRefreshRefusesWhenTheRetryFails`. After `YOLO_USE_INSTALLED` handled a failed background refresh, the launcher still checked whether another refresh was due and announced/scheduled one; the test then found the failed-result file still present (`err == nil`). This is a real sequencing regression, not a timeout or native-test compile failure. See the [generated-launcher test](../../internal/entrypoint/prelaunchrefreshtiming_test.go#L334-L373) and [refresh caller](../../internal/entrypoint/prelaunchrefresh.go#L613-L628).
- **The same run's Linux job 118483596858** failed `TestStopHomeProcessesWaitsForAScratchRemover`, reporting `stopped [pid 12819 ()]`. That output does not prove a signal reached a live process: the old helper read existence and arguments separately, then treated empty or unreadable arguments as an ordinary worker. The exact interleaving is unknown. See the [cleanup helper](../../integration/preparationworkers_test.go).

## Fixed and checked

Commits `d57976593cfa606dbbe85bd1832274731848a6a6`, `903a35b020bf42c0374da224f6fc4bc06e51f585` and `0de3f095c7658adc449bb83fc4d29fec308b42a4` repair the cached-link, shell-pattern, bounded-probe and readiness fixtures above.

Commit `6ddb485188c638a9586469ae023f9e5a6e2cc0cc` fixes the launcher sequence: when the installed-version hatch handles a failed background result, that invocation returns before due checks can queue a replacement refresh. This follows the existing invocation-scoped contract in [PD-NF1 and PD-NF2](../design/program-delivery.md#decision-ledger); it does not change the default refusal, future launches or `agent_updates` behavior. The new generated-launcher assertion failed before the fix and passed 25 repetitions after it. On the final combined source, `just check-ci` passed, including Linux/Darwin vet and staticcheck; the failed historical macOS CI test has not been rerun natively.

Commit `010ab75ccc8a6b83e076051c38468c4226b1b724` adds two cleanup-helper safety fixes and permanent tests: a live scratch remover surviving the bound is an error without a signal, and a live process whose current argv is empty cannot inherit stale scratch-remover classification. Existing PID-identity, HOME, disappearance and signal-error checks remain. The helper reports uncertain live processes rather than signalling them. In a prior full integration run at that point, `TestAJailRunsAPackBinaryItDownloaded`'s cleanup reported a live pid with empty argv because the process listing could not reverify its HOME. The exact interleaving is unknown; one focused rerun passed, which is not proof the full-suite failure is resolved.

A separate fixture omission caused an earlier full-suite failure: `TestHostFloorInstallsTheVendorsRelease` selected host commands without opting into `host_management: "own"`. Commit `6ac7df376e2674715cc9ab844836bec261d6b0e1` adds that explicit opt-in; the focused vendor-host test passed. The full integration run on that source still failed in the cleanup test above after 938 seconds. A focused rerun taking about 15 seconds passed, but did not establish that the full-suite failure was resolved.

The cleanup observation now has a bounded test-only repair in commit `be367cee9427a56f03fcb534ce1d1ec0fefdaec9`. Its actual parent is `92fe4f04055ea05ddccccba693774d0b8421df51` (the existing report update after `6ac7df3`), so the approved source commit was already based on the current primary; no redundant replay was needed. Primary `main` fast-forwarded from `92fe4f0` to `be367ce` and remained clean. On that exact landed source, `just check-ci` passed in 235 seconds and `YOLO_TEST_REAL_PACK_INSTALLS=1 go test -count=1 -timeout 0 ./integration` passed in 934.621 seconds (935 seconds elapsed). Before landing, the count-one `TestStopHomeProcesses` tests, Darwin/arm64 integration compile, `just format` and `git diff --check` also passed. This is the first passing full integration result recorded here for the source containing both the helper retry and the vendor-host fixture opt-in.

The source diff from `6ddb485188c638a9586469ae023f9e5a6e2cc0cc` through `be367cee` is empty for `cmd/`, `internal/`, `packs/`, Go module/vendor inputs and flake files. The final verification therefore did not rebuild or reload an image or repeat a nested-jail launch for this test-and-report-only change.

The later ARM CI failure on `1c14fbf6ba836064930241562d90f752c9ccfdb8` was in `TestAttachDeliversTheSelectedProfile` cleanup: Podman PID 13064 was reported live with an empty argument vector, which the old helper could not classify. The CI log did not include process flags, a start-time bracket or HOME observations, so it does not establish which process state caused that failure. A separate kernel-exit experiment established that an exiting process can remain observable; it does not show that this was PID 13064's state in CI.

Commit `b807913a8f9f5ea49e169f9f2385bfd13527f242` narrows the cleanup exception: ownership requires a coherent HOME observation bracketed by matching start times, and Linux `X`/`x` are not accepted as live states. Its focused regression tests failed before the fix and passed after it; the short integration suite and Darwin/arm64 integration compile also passed on that candidate. These results establish a green local full suite on `b807913`; they do not identify the cause of a historical Podman cleanup failure or establish its exact process flags, identity or HOME evidence.

A full integration run recorded on historical `cd8b2fe` completed in 760.438 seconds; a later full run on `6ae4053` failed. The available results do not establish the cause of that failure. Separate targeted tests demonstrate the bounded kernel-exit retention behavior and the new ownership/state gates, but they are not evidence that the Linux stat [`PF_EXITING` bit](../../integration/preparationworkers_test.go#L92), PID reuse, or a HOME mismatch caused either historical full-suite result.

## Limits

The two earlier full integration runs on a stale isolated checkout at `6ddb485188c638a9586469ae023f9e5a6e2cc0cc` took 943 and 907 seconds; they lacked both `010ab75`'s helper changes and `6ac7df3`'s fixture opt-in. The first also hit a legacy broker-fixture failure; five focused reruns passed, and a later 26-repeat cleanup test passed without a source change between repetitions. Those focused results do not replace the full run on current source. The 938-second full run on `6ac7df3` did fail at the cleanup observation; its roughly 15-second focused rerun was not proof of a full-suite fix. The exact original process-listing interleaving remains unknown. The later 760.438-second run on `cd8b2fe` and failure on `6ae4053` likewise do not reveal the historical failure's process flags, identity or HOME observations; the new tests validate the repaired contract, not a retrospective causal diagnosis.

Native macOS execution and a rootless-host run have not been repeated. The Darwin/arm64 `go test -c` result proves compilation only, not native behavior; the full integration pass on `b807913` was on Linux. No new binary, image build, or nested-jail launch was part of this test-and-report-only verification. The original 0.15.0 eligibility attempt, request 39359972447/1, stopped because exact-SHA CI was not green ([workflow](../../.github/workflows/release-request.yml)); these local results make no claim about a later hosted CI run, release readiness, or publication.
